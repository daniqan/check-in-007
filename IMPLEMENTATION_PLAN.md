## 1. Overview

This cycle adds offline multi-device check-in log consolidation for event operators who
run the kiosk on more than one iPad. Today each device stores its own
`checkin007.log.v1` array and can export CSV/JSON, but there is no in-app way to merge
those exports into a canonical event log. The new tooling will let an admin import one or
more exported log files, preview merge results, apply a deterministic deduplicated merge
to local storage, and export the consolidated log without sending guest or attendance
data over the network.

## 2. Scope

### In scope

1. Add an admin-only "Merge Logs" workflow reachable from the existing admin dialog.
2. Accept one or more `.json` and `.csv` files generated by this app's current export
   buttons.
3. Parse log rows into the existing canonical shape:
   `{ visitId, guestId, name, table, timestamp }`.
4. Deduplicate by `visitId` first, then by `guestId + timestamp` when a legacy or edited
   file has a blank visit id.
5. Sort the merged log by timestamp ascending, with deterministic tie-breaks by
   `guestId`, normalized `name`, `table`, and `visitId`.
6. Show an accessible merge summary before applying: current local count, imported row
   count, accepted new row count, skipped duplicate count, skipped invalid row count, and
   parse errors per file.
7. Apply the merge only after explicit confirmation, persist through the existing store
   abstraction, and keep `exportLogCsv()` / `exportLogJson()` as the canonical export
   surface.
8. Add unit tests for parsing, normalization, dedupe, invalid input handling, ordering,
   and store integration.
9. Add an end-to-end test that creates local entries, imports two overlapping log files,
   confirms the merge, and verifies the copied/exported consolidated CSV exactly matches
   storage.

### Out of scope

- Live device synchronization, peer discovery, Bluetooth, AirDrop automation, WebRTC, or
  any network transport.
- Conflict editing UI beyond deterministic duplicate skipping and invalid-row reporting.
- Changes to the roster CSV import format.
- Optional scan audio, native SwiftUI iPad build, offline static-HTTPS helper, and Node
  24 LTS toolchain bump.
- Schema migration from `checkin007.log.v1`; this cycle keeps the existing storage key
  and row shape.

## 3. Architecture

The app remains a zero-runtime-dependency, single-file-capable web app. Merge logic is
split into a pure library, store methods, and a thin admin UI integration.

```text
Admin Merge Logs input
  -> File objects selected by operator
  -> file.text()
  -> parseLogFile(name, text)
  -> mergeLogEntries(existingLog, parsedRows)
  -> preview summary in admin dialog
  -> confirmed store.mergeLogEntries(rows)
  -> localStorage checkin007.log.v1
  -> existing CSV/JSON export/copy buttons
```

Ownership boundaries:

- `src/lib/log-merge.mjs` owns parsing app-exported CSV/JSON, canonical row
  normalization, validation, dedupe keys, summary counts, and deterministic ordering.
- `src/lib/store.mjs` owns persistence and exposes a small merge API that calls the pure
  merge helper against `loadLog()` and `saveLog()`.
- `src/screens/admin.mjs` owns file input handling, preview rendering, confirmation, and
  accessible status updates.
- `src/lib/csv.mjs` remains the shared CSV parser/serializer; no second CSV parser is
  introduced.
- `scripts/build.mjs` owns bundle module order and must include `src/lib/log-merge.mjs`
  before `src/lib/store.mjs` if `store.mjs` imports it.

Failure domains:

- File parsing failures are isolated to the selected file; one bad file does not block
  valid rows from other selected files, but the preview must disclose the file error.
- Invalid rows are skipped, counted, and not persisted.
- Storage failures continue to use the existing volatile-memory fallback in
  `createStore`; merge behavior must work in both persistent and volatile modes.
- If the admin closes the dialog before confirming, parsed rows are discarded and local
  storage is unchanged.

## 4. Technical Decisions & Rationale

1. **Manual file import/export instead of network sync.** The backlog asks for
   consolidation/merge tooling, and the project already supports offline file exports.
   Manual file selection preserves the current privacy posture and works from `file://`
   or local HTTPS without server setup. Alternatives such as WebRTC or cloud sync add
   pairing, availability, and security work that belongs in a separate cycle.

2. **Use `File.text()` / `Blob.text()` rather than `FileReader`.** MDN documents
   `FileReader` as asynchronous file reading but also notes `Blob.text()` as the newer
   promise-based API for reading file contents as text:
   https://developer.mozilla.org/en-US/docs/Web/API/FileReader/readAsText. Promise-based
   reads fit the existing `async` admin import code and avoid event-handler state.

3. **Reuse existing Blob URL downloads with explicit revocation.** The current
   `downloadText()` function creates a Blob URL and revokes it after triggering download.
   MDN documents that `URL.revokeObjectURL()` releases a URL created by
   `URL.createObjectURL()`:
   https://developer.mozilla.org/en-US/docs/Web/API/URL/revokeObjectURL_static. The merge
   cycle keeps this pattern and does not introduce FileSaver or another dependency.

4. **Keep localStorage as the only durable store.** MDN describes `localStorage` as
   origin-scoped storage persisted across browser sessions:
   https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage. The app already
   wraps it with a memory fallback, so the merge API extends that wrapper instead of
   adding IndexedDB. IndexedDB would offer larger quotas and transactions, but expected
   event logs are small enough for JSON-array rewrites and the simpler store keeps the
   static artifact lightweight.

5. **Deterministic last-write-free merge.** Check-ins are append-only attendance facts,
   not mutable records. The merge should never overwrite one row with another; it accepts
   the first canonical row for a dedupe key after sorting inputs by source order and row
   order, then sorts final output for operator readability. This avoids clock-conflict
   prompts while still producing repeatable output in tests.

6. **No new runtime dependencies.** Existing `node:test`, Playwright, `axe-core`, Acorn,
   and Prettier remain sufficient. Adding Papa Parse or a UI framework would increase
   bundle size and duplicate capabilities already covered by `src/lib/csv.mjs`.

Acceptance criteria:

- Empty imports return zero accepted rows and do not mutate existing entries.
- Duplicate `visitId` rows are skipped even if name/table differ.
- Blank-visit legacy rows dedupe by normalized `guestId + timestamp`.
- Invalid JSON produces a file-level error in the admin preview.
- CSV files missing a required column produce a file-level error.
- Invalid rows count includes missing `guestId`, missing `name`, missing `timestamp`, and

- Final merged output is deterministic for identical inputs.

## 7. Integration Points

1. **Admin file input -> parser**
   - Contract: browser supplies `FileList`; each `File` supports `text()`.
   - Failure mode: unsupported or unreadable files appear as file-level errors.
   - Migration path: roster CSV import remains a separate input and code path.

2. **Parser -> merge helper**
   - Contract: parser returns canonical-ish rows plus invalid-row metadata.
   - Failure mode: missing columns, invalid JSON, and invalid timestamps are counted and
     displayed, not persisted.
   - Migration path: existing app-exported CSV/JSON files remain valid inputs.

3. **Merge helper -> store**
   - Contract: store passes `loadLog()` rows and imported rows into
     `mergeLogEntries()` and persists only returned canonical entries.
   - Failure mode: storage exceptions trigger the existing volatile fallback.
   - Migration path: storage key remains `checkin007.log.v1`; no schema migration is
     required.

4. **Store -> export/copy**
   - Contract: export methods read the stored merged log and serialize the same columns.
   - Failure mode: malformed pre-existing local rows are skipped during merge preview and
     excluded from the persisted merged result only after explicit apply.
   - Migration path: users who never use merge see unchanged export behavior.

5. **Build transform**
   - Contract: every imported module appears earlier in `scripts/build.mjs`'s `modules`
     array.
   - Failure mode: wrong ordering causes undefined namespace aliases in `dist/index.html`.
   - Migration path: unit build tests and `npm run build` catch residual module/order
     regressions.

## 8. Error Handling & Edge Cases

- **No files selected:** leave apply disabled and show no-op status.
- **Unsupported extension:** attempt content-based parsing; if both paths fail, show a
  file-level error.
- **Invalid JSON:** catch `JSON.parse` errors, report the file name, and continue other
  files.
- **CSV missing required columns:** report a file-level error and accept no rows from that
  file.
- **Empty files:** count as a file-level error for JSON and a missing-column error for CSV.
- **Row missing guest id/name/timestamp:** skip row, increment invalid count, and keep
  processing.
- **Invalid timestamp:** skip row; do not invent timestamps during consolidation.
- **Duplicate rows across devices:** skip by deterministic dedupe key and count as
  duplicates.
- **Duplicate rows inside one imported file:** same duplicate handling as cross-file rows.
- **Malformed existing local rows:** preview discloses invalid existing-row count; apply
  persists only canonical merged rows so future exports are clean.
- **Storage blocked/quota errors:** use the current volatile fallback; status should still
  report completion, and `store.isVolatile()` remains available for tests.
- **Dialog close during preview:** remove preview DOM and cached rows with the dialog.
- **Large imports:** process synchronously but bounded to text parsing and array sorting;
  no network or timers are introduced.

## 9. Stability & Performance

Expected event size is small: hundreds to low thousands of log rows per device, with a
reasonable upper bound of 10,000 total rows for planning and tests.

- Parsing is `O(total characters + rows)` per file.
- Dedupe is `O(n)` with a `Map`/`Set` over normalized keys.
- Final ordering is `O(n log n)` by timestamp and stable tie-break fields.
- Memory is `O(n)` for parsed rows, dedupe keys, summaries, and the merged array. For
  10,000 rows at roughly 250 bytes per canonical row plus JS overhead, expected peak
  memory is comfortably below tens of MB on a modern iPad.
- No object URLs are created by import parsing; existing export downloads continue to
  revoke Blob URLs immediately after link click.
- No persistent event listeners are added outside the admin dialog. Closing the dialog
  removes the merge input, buttons, cached rows, and preview markup.
- The workflow degrades gracefully: bad files and rows are reported while valid files can
  still be applied.

Rollout procedure:

1. Build the artifact with `npm run build`.
2. Smoke-test the admin merge workflow from `http://localhost:8080`.
3. Open the built `dist/index.html` from `file://` and verify the app reaches the roster.
4. Distribute the new artifact to event devices.

Rollback procedure:

- Revert the merge cycle commit and rebuild `dist/index.html`.
- Existing `checkin007.log.v1` data remains readable because the row shape and key do not
  change.
- If a bad merge was applied during an event, restore from the JSON/CSV exports retained
  from each device and re-run consolidation after the fixed build ships.

## 13. Open Questions

1. **Should duplicate rows with same `visitId` but different guest details be surfaced as
   conflicts?**
   - Proposed resolution: this cycle counts them as duplicates and keeps the first
     canonical row because app-generated visit ids are intended to identify one
     immutable check-in fact.
   - Information needed to change: evidence that operators manually edit exported files
     and need conflict repair in-app.

2. **Should the merged output preserve source-device labels?**
   - Proposed resolution: no. Existing exports do not contain a device id, and adding one
     would change the canonical row schema.
   - Information needed to change: a future requirement for per-device audit trails.

3. **Should invalid existing local rows be auto-cleaned during preview?**
   - Proposed resolution: no mutation during preview. Cleanup happens only after Apply
     Merge, when the operator has confirmed the merge.
   - Information needed to change: a requirement for automatic repair on admin open.
